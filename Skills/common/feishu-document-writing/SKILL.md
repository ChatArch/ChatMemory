# Feishu Document Writing

## 定位

本 Skill 负责“飞书文档是否真正写得好”，不替代飞书文档 API、权限或媒体上传工具的操作规范。

开始前：

1. 如果任务属于 Playground，先建立或确认对应 Project，并遵循工作区 `AGENTS.md` 与 `projects/README.md`。
2. 加载当前环境的飞书文档操作 Skill，读取其最新 XML、样式、创建/更新和媒体插入规则。
3. 涉及在线协作、项目记录或主文档回链时，同时加载 `feishu-collaboration-documents`。
4. 不把聊天长回复或本地 Markdown 原样倾倒进飞书；先完成信息设计。

## 内容设计

### 内容优先，不套模板

先判断受众、阅读目的、素材形态和用户要做出的判断，再选择段落、表格、列表、图片或图示。结构化组件只用于降低理解成本，不为了“看起来丰富”而堆叠。

用户给出样例、已有文档或明确风格时优先沿用。没有明确要求时，不强制固定开头、固定章节数或固定富文本比例。

### 第一屏快速建立理解

较长报告通常应在开头提供：

- 清晰标题与研究范围；
- 一句话核心结论；
- 3–6 条关键发现或一张简短速览表；
- 数据口径、时间和来源边界。

正文再展开证据、方法、限制、风险和建议。移动端阅读时控制标题深度、段落长度和表格宽度。

### 选择正确表达形式

- 叙述、分析、解释：使用有承接关系的段落，不要把每句话拆成项目符号。
- benchmark、规格、价格、任务对比等真正的行列数据：使用表格。
- 真正并列的结论、步骤或清单：使用列表。
- 关键限制、风险或必须注意的数据口径：少量使用 callout。
- 流程、架构、时间线、因果链、能力分层：图示明显更清楚时使用图或画板。
- 长引用、代码、公式：使用对应原生块，不用普通段落模拟。

全文保持同一套标题和编号层级，不滥用“小标题 + 一句话”。

## 截图、图片与图表

用户要求完整报告、重要截图或图片时：

1. 优先使用官方原图、官方 benchmark 图、产品截图和 System Card 图，不用无来源装饰图替代证据。
2. 图片放在对应论点附近，不统一堆到文末。
3. 每张图提供简短 caption：展示什么、为什么重要、来源是什么。
4. 可基于官方数据制作二次可视化，但必须标注“根据官方数据整理”，不能伪装成官方图。
5. 对比截图要写清输入、基线、目标模型和观察点，不能只放图不解释。
6. 外部图片先保存到 Project 的 `reports/assets/`，再通过文档媒体流程插入；原始 URL 保留在来源清单中。
7. 上传前检查分辨率、裁切、文字可读性，以及是否包含隐私、凭据或其他敏感内容。

## 调研型报告质量线

报告必须区分：

- 官方明确披露的事实；
- benchmark 的测试设置和脚注；
- 基于证据的分析；
- 尚未披露、不能确认的部分。

模型或技术产品报告至少检查：

- 模型定位、版本和可用范围；
- 代表性 benchmark、基线和增量；
- reasoning effort、工具配置、Agent 数、时间上限等设置差异；
- 方法或系统创新；
- 成本、延迟、上下文和 API 规格；
- 安全评测、失败案例和已知退步；
- 哪些榜单并未领先；
- 第一方自报、内部数据集和外部独立评测之间的区别。

不要把“结果提升”包装成未公开的架构创新。参数量、网络结构、训练数据规模或训练配方未披露时，明确写“官方未披露”。

## 链接与引用

- 正文首次出现关键概念时提供对应官方链接。
- 文末按“发布稿 / System Card / API 文档 / benchmark / 其他来源”分组列出来源。
- 链接标题说明目标内容，不使用含糊的“点击这里”。
- 重要数字应能追溯到官方表格、图或原文。
- 不同官方页面因模型快照、reasoning effort 或配置不同而出现数字差异时，保留并解释差异，不擅自挑选一个掩盖。

## 发布流程

1. 在 Project 中保留研究稿、富文本源和 `reports/assets/` 素材。
2. 使用当前飞书文档工具支持的 XML/rich-block 流程创作文档。
3. 长文档按章节顺序维护，避免并行撰写造成重复或口径冲突。
4. 在对应章节插入关键图片、图表和来源链接。
5. 创建或更新在线文档后立即 Fetch 回读，验证标题、章节、表格、图片、caption、链接和图示。
6. 检查没有遗留占位符、降级警告、空章节或被拆坏的表格。
7. Playground 任务将最终链接写入 `progress.md` 和 `reports/links.md`，并按协作规范回链主文档。

## 交付前自检

- 第一屏能否让读者在一分钟内理解结论？
- 事实、分析与推断是否区分清楚？
- benchmark 是否说明配置差异，而不是只列高分？
- 是否同时呈现优势、非领先项和风险？
- 图片是否真正提供证据，并有 caption 与来源？
- 表格是否适合移动端，列数是否过宽？
- 是否存在 Markdown 倾倒、组件堆砌或装饰性图片？
- 飞书在线文档是否已回读验证，而不只是命令返回成功？
